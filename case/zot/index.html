Digital Transformation of a Corporate Employee Benefits System

A benefits policy amended every year — building a system that doesn't need an engineer each time it changes | Lead Product Designer, working with PM, Frontend, and Backend

3 Months Figma B2B SaaS

Rapid Digital Workflow

Consolidated a 10-step paper approval process into 5 tracked steps, with status visible at every stage.

Automated Rule Engine

Systematic logic automatically filters eligibility, blocking invalid requests at the source to eliminate human error.

One-Click Financial Reporting

Automatically generates bank transfer files and tax filing data, significantly easing cross-departmental reconciliation.

The Challenges

9

Pages of Data-Output Spec

The client's spec covered monthly reports, split routing, export fields. Thorough on how data flows — but it never said who does what, in what situation. That layer had to be built first.
6

Benefit Types, Each Tiered Differently

Tiered by tenure, by relationship, by number of children, by two separate start-date cutoffs — plus a raffle with its own eligibility and exclusion lists.
10+

The Rules Get Rewritten

The raffle's exclusion clause was added last year. The travel cutoff changes annually. But the change has a boundary: a wedding gift is always "tenure → amount" — only the numbers move. Structure stable, parameters not. That distinction decided the architecture.

UX Planning

Turning a feature list into operational scenarios

Translating the Feature List Into User Tasks

I mapped what each role actually does on each screen, and used it to separate necessary functions from nice-to-haves.
The list never defined who could create versus only view, or what someone sees when they're both a committee member and an employee. One outcome: in-app chat was cut — the client preferred email and didn't want the review flow carrying messaging overhead.

Bringing In Wireframes Early So Discussion Had Something to Look At

The client struggled to picture outcomes from process diagrams alone, so I brought in low-fidelity wireframes earlier than planned. Abstract permission and state discussions moved faster with something concrete on the table.

Keeping Excel, Rather Than Replacing It

Roster cross-checking already happened in Excel. My instinct was to bring it all on-platform — once you're digitizing, two tools scatters the data.
The client checked with the people who actually do it; feedback favored keeping it (relayed by the client, not a direct interview). We kept upload/export. Optimizing for system purity isn't optimizing for the person doing this every month.

Design Iterations

Three decisions, one standard: optimize for the common case, not the exception

Condition Architecture: Where to Invest Flexibility

The Original Plan: A Universal Condition Combinator
My first design was a composable rule builder — combine tenure, employee type, department, past counts like a filter. Zero engineering for future changes. But that flexibility is paid upfront: the backend needs every validation type built in advance, for combinations that might never get used.
Independent Setting Pages, Four Layers
The client judged the cost wasn't worth it and I accepted that call. Looking back, the reason it held wasn't "the rules don't change" — they do — but that only parameters change, not structure. Four layers: hardcoded baseline, editable tiers, context options a human verifies, and evidence that was never going to be machine-validated. New options still need engineering — the bill is paid per benefit, not once upfront.

Collapsing the Approval Panel for the High-Frequency Case

A Complete, Independent Approval Page
Approval was its own page — every sign-off record visible, logically complete. Walking the scenario through with the client (their report, not my observation): reviewers kept switching between application data and the panel to compare tenure and amounts.
A Floating, Collapsed Sign-off Panel
Multi-level sign-offs are rare; routine checks are frequent. The dedicated page solved for the minority at the majority's expense. A floating panel that follows the scroll keeps review and sign-off on one screen — trading layout completeness for continuity.

Moving Validation Earlier, Not Deeper Into the Flow

Validating at Step One of the Application
The original design validated at step one of applying — pick a benefit and tier, and the system flags a mismatch. Built to prevent the exception: someone applying for what they don't qualify for.
Validation Moved Up to the Application List
Most applicants pick correctly, so designing around the minority made everyone walk an extra step. Ineligible items are now unclickable on the list; eligible ones auto-populate the amount. Shorter path for the applicant — and it removed the committee's manual tier cross-check entirely.

A State Conflict: The Recall Mechanic

Edits During Review Break the Reviewer's View
If an applicant edits a case already in review, what the reviewer sees drifts from what exists.
Recall Before Edit
Editing requires recalling first, which pulls the case out of the queue. Every status now has one unambiguous meaning, and each state change gives notifications a clean trigger.

Attachment Governance: Reducing Reviewer Cognitive Load

Generic Filenames Forced Reviewers to Open Every File
Attachments named "photo.jpg" meant opening every file just to identify it — slow, and error-prone in a busy cycle.
Mandatory Category Tags at Upload
Attachments must now be tagged by category on upload. Slightly more work for the applicant, considerably less scanning for the reviewer.

Project Outcomes

Structural comparison, not post-launch measurement — the system is in acceptance testing
5
Steps, Down From 10
A structural comparison, not a measurement. Everything removed was routing or notification. The system replaced the moving of paper, not the decisions.
1
Review Step Removed by Design
The other four would disappear in any digitization effort. Only the committee's eligibility cross-check needed a design decision — the client's spec had planned to keep it.
4
Condition Layers
Baseline, tiers, context, evidence. The two middle layers are committee-editable — exactly where the yearly changes land.
3
Metrics Queued for Launch
Sign-off time, rejection rate, and how often the list blocks an ineligible submission — the last directly tests whether moving validation earlier worked.

Known Limitations

What this architecture costs, and where it will need revisiting
A Hidden Coupling Between Baseline and Tiers
"Three months' tenure" is hardcoded, so the first tier counts from month 3, not month 0. Change the baseline and the tier starting points need updating too — nothing in the interface surfaces that dependency.
Shared Fields Repeat Across Rows
Fields like "application count" repeat on every row instead of being lifted out. A deliberate trade for self-contained rows, at the cost of visible duplication.
Context Options Can't Be Added by the Committee
Options are defined at development time. The committee can enable and price them, but a genuinely new scenario needs engineering. The direct cost of dropping the combinator — valid only while rule structures stay stable.
