UX Planning

Mapping tasks before screens, then cutting scope with evidence

Mapping Clinical Tasks Before Any Layout Work

I mapped user journeys across clinical scenarios first, aligning stakeholders on what the system was and wasn't responsible for before any screen was designed.
This surfaced an early scope decision: nurses already log incidents in existing hospital systems, so I cut the log-management module and freed the screen real estate for the monitoring view.

Defining "Clear" for a Screen Read at a Distance

The client's spec was hardware-driven — data fields and features, no reference to how the screen would actually be read. Before deciding what belonged on it, I defined the real reading condition: a nurse walking past, several metres away, a few seconds. Everything downstream was tested against that, not a checklist.

Iterations

Three versions, tested against how the screen is actually read

Version 1 — My Assumption Was Wrong

The Assumption
First instinct: surface Uneo's bed-pressure sensing data prominently — the thing the hardware does best.
What Sales Found
Nurses wanted every bed visible at once, not a detailed readout — my layout required scrolling. The focal point should be what the user needs next, not the feature the hardware is proudest of.

Version 2 — Testing an Assumption, Not Just an Opinion

The Assumption vs. the Client's Instinct
I flagged that this version carried too much information per bed card. The client wanted to try it as-is first — so it shipped, and I set out to test whether my assumption held.
First Heatmap Read: 54
Ran it through eye.ai. Attention wasn't concentrating on the bed cards — the first piece of evidence for the assumption.
Then Tested at the Actual Reading Distance
Projected the design onto a TV and asked nurses to view it from where they normally walk past — no fixed distance, no scripted task. Feedback was consistent: too much information, hard to read. Bed number is the only thing that really matters — everything else gets re-checked at the bedside.

Version 3 — De-cluttering, a Stakeholder Conflict, and a Second Read

De-cluttering & Status Sorting
Removed non-critical metrics from bed cards, kept bed number and alert state, added Status sorting (Alerts / Attention / Disconnected / Normal / Vacant).
Second Heatmap Read: 42 — Lower Score, Better Result
The score dropped from 54 to 42. The tool's reasoning didn't hold up here — it flagged a small heading and a lack of on-screen buttons, but this screen's action is walking to a bed, not clicking. The heatmap itself told a different story: attention concentration on bed cards visibly improved.
A Separate Issue: the Alert-Management Panel
Unrelated to the bed-card work above — PM/leadership saw the alert-management panel as a commercial differentiator; Sales/users said the 40-bed grid was already cramped. Made it collapsible: expanded for desk use, collapsed for full-width ward monitoring.

Outcomes

Deployed, and what I'd examine if I ran it again
15
Nursing Facilities, ~50 Nursing Staff
Deployed across 15 different facilities means 15 different ward layouts, staffing patterns, and existing workflows. The "readable at a glance, from across a room" constraint had to hold across all of them, not just the one it was tested in.
3
Iterations — All Before Development
The three versions documented above happened during design, where changes are cheap. Once the direction was confirmed, the front-end build proceeded without rework caused by feasibility issues, because technical constraints were checked with the backend team at the wireframe stage.
1
Person Designed and Built It
Development moved faster than it otherwise would have, for a specific reason: the components and styles were already defined, and the person building was the person who'd defined them. There was no handoff-translation step. I'm not putting a percentage on this — it wasn't measured, and there's no comparison case — the mechanism is the claim, not a number.
42
The Score I Shipped Despite It Being Lower
Attention-modeling tools carry assumptions about what an interface is for. When the model's assumptions didn't match how this dashboard is actually used, I read the underlying heatmap instead of the aggregate score — and shipped the version that put attention where the task needed it.
